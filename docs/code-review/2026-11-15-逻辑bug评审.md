## 1. BUG-1（P0，server）：push 不校验实体归属 vault —— 跨 vault 明文泄露与越权删除

**位置**：`server/src/store/syncstore.ts`（`pushItem` 整个函数）

- `syncstore.ts:141-147`：行存在性检查 `SELECT rev, deleted_at FROM ${ent.table} WHERE id = ? FOR UPDATE` —— 只按 `id`，**不过滤 `vault_id`**；
- `syncstore.ts:200-206`：删除活行路径同样无归属检查，`base_rev` 也不参与（见 BUG-2）；
- `vaultId` 仅在 `insertEntity`（新行落库）与 `allocRev`（changes 行打标）时使用，对已存在实体完全是摆设。

**影响**（已实测证实）：
1. **跨 vault 读**：攻击者 vault 对他人实体 id 发 `op=upsert, base_rev=0`，实体存在 → 走 conflict 分支，`syncstore.ts:164-173` 的 `conflict()` 通过 `db.scanEntityRow` → `rowToWire` → `decodeCell` 返回**解密后明文**（`server_data` 含 `password_enc` 明文、hostname、notes 等）。实体 id 是 UUIDv7（时间前缀可预测），并非不可猜测。
2. **跨 vault 写/删**：直接 `op=delete` 即可删除他人 vault 的实体（返回 ok）；由于 changes 行打的是**攻击者**的 vault_id，受害者的 pull 永远收不到墓碑通知，静默数据丢失。

**期望语义依据**：
- `docs/plan/eterm-技术方案.md:548`（威胁模型表）："vault 维度鉴权（token ↔ user ↔ vault 归属校验）" 是承诺的越权防线；
- 架构铁律（AGENTS.md/PRD）：中枢是多端同步枢纽，vault 即租户边界。

**复现与实测输出**（同库两个 vault，userB 对 userA 的实体操作）：

```
BUG-1a 实际返回: {"status":"conflict","rev":1,"serverData":{"id":"01a1…","vault_id":"01a1…(userA)",
  "label":"root","username":"root","password_enc":"TOPSECRET-pw",…}}
BUG-1b 跨 vault delete 实际返回: {"status":"ok","rev":2}
BUG-1b victim vault changes: []   ← 受害者收不到任何删除通知
```

**修复建议**：`pushItem` 的行查询与删除/更新/复活各分支统一加 `AND vault_id = ?`；行不存在或归属不符时按 `entity_not_found` 拒绝（对 base_rev=0 的新建照常插入）。conflict 响应前同样先确认归属。

## 2. BUG-2（P1，server）：`op=delete` 不校验 base_rev —— 陈旧删除静默覆盖并发更新

**位置**：`server/src/store/syncstore.ts:200-206`（活行删除分支）

活行删除只置 `deleted_at` 并分配新 rev，**全程未比较 `item.baseRev` 与 `curRev`**。对比：
- 同函数复活路径（`syncstore.ts:193`）`if (curRev !== item.baseRev) return await conflict();` —— 墓碑上的 upsert 有乐观锁；
- 存活行 upsert（`syncstore.ts:207`）也有 —— 唯独 delete 没有，行为不对称。

**影响**：设备 A、B 各持 rev1；B 更新到 rev2 后，A 持陈旧 base_rev=1 发 delete → 服务端 ok，B 的更新被静默删除。多端场景（本项目核心卖点）下是确定性丢数据路径。

**期望语义依据**：`docs/plan/eterm-技术方案.md` §3.3 push 语义：
> 1. `base_rev` 校验：客户端所见版本。…… 2. 版本不符 → `conflict` + 附服务端当前 `server_data`；

该条未把 delete 排除在校验之外（第 5 条只说 delete 落墓碑的动作，不豁免第 1 条）。若确属"删除永远赢"的设计，也应显式写进方案并与复活路径的对称性说明，目前代码与其自身文档矛盾。

**复现与实测输出**：

```
BUG-2 陈旧 base_rev 删除实际返回: {"status":"ok","rev":3}   （期望 conflict）
BUG-2 changes 序列: [{"op":"delete","rev":1},{"op":"delete","rev":2},{"op":"delete","rev":3}]
```

（注：pull 对历史 upsert change 也回 `op=delete`，因为 `fetchChanges` 按行**当前**状态推断 op——这本身是协议行为，但加剧了"B 的更新在事件流里无痕消失"。）

**修复建议**：活行 delete 增加 `curRev !== item.baseRev → conflict`（同复活路径）；若要保留"删赢"，至少需在方案中明示并给 delete-after-update 一个可审计的事件。

## 3. BUG-3（P1，server）：ssh_key 墓碑复活绕过密钥内容不可变校验

**位置**：`server/src/store/syncstore.ts:186-197`（复活分支）与 `225-255`（`checkKeyImmutability`）

`checkKeyImmutability` 只在**存活行 upsert** 路径被调用（`syncstore.ts:208`）；`deleted_at != null` 的复活分支（`syncstore.ts:186-197`）直接 `updateEntity(..., resurrect=true)`，新 `private_enc` 原样覆盖。

**影响**：密钥删除后（客户端重试/多端竞态/恶意构造）可借"复活"改写私钥内容，破坏密钥版本链（`key_version`/`superseded_by` 语义作废），并绕开 F4.4 之外的审计预期。

**期望语义依据**：
- PRD `docs/eterm-产品设计与需求文档-v2.md:131`："密钥对象按**不可变版本化**处理：私钥内容一旦创建不覆盖，修改 = 新版本指向"；
- `docs/plan/eterm-技术方案.md:258`："`ssh_keys.key_version`：私钥内容不可变（PRD §3.4）。'修改私钥' = 新行（新 id）+ `superseded_by` 链"。

**复现与实测输出**：

```
BUG-3 复活实际返回: {"status":"ok","rev":3}        （期望 rejected："密钥内容不可变…"）
BUG-3 复活后 private_enc = "KEY-REPLACED"          （原值 KEY-ORIGINAL 被覆盖）
```

**修复建议**：复活分支对 ssh_key 同样调用 `checkKeyImmutability`；或复活时强制要求 data 不含密钥内容列（改内容必须走新 id）。

## 4. BUG-R1（P2，rust）：`first_seen`/本地事件时间戳日期恒差一天

**位置**（同一算法的两份拷贝，缺陷相同）：
- `client/app/rust/src/api/ssh.rs`：`chrono_now_rfc3339`（→ 本次评审为可测性拆出纯函数 `rfc3339_from_unix`，逻辑未改动）——known_hosts 的 `first_seen`；
- `client/app/rust/src/store/mod.rs:303-325`：`super_utc_now_rfc3339`（523a4bd 新增的 events 表时间戳）——Logs 页事件时间。

原实现的日历换算把**0 基的 day-of-year 直接当作"几号"**输出：年循环结束后 `d` 是年内第几天（0 基），月循环减去各月天数后余数 `d` 直接进 `format!("{d:02}")`—— January 1st 算出 `d=0` → 输出 `1970-01-00`；此后任何日期都显示为前一天。

**影响**：Known Hosts 页 `first_seen` 与 Logs 页事件时间全部早一天；当天记录显示 `MM-DD-00` 形式的非法日期（如 2026-11-15 显示为 `2026-11-14`）。

**复现与实测输出**（`cargo test --lib`，`#[should_panic(expected = "BUG-R1")]` 用例常驻运行；该测试已随 523a4bd 入库）：

```
BUG-R1: first_seen 日期差一天：期望 1970-01-01T23:59:59Z，实际 1970-01-00T23:59:59Z
```

（第二断言：`rfc3339_from_unix(1_794_700_800)` 期望 `2026-11-15T…`，实际 `2026-11-14T…`。`store/mod.rs` 的拷贝算法逐行相同，一并受影响。）

**修复建议**：两处收敛为一个公共函数（`util`），格式化前 `d += 1`（或改用成熟时间库）。修复后删除用例上的 `#[should_panic]`。

## 5. BUG-D1 / BUG-D2（P2，flutter）

### BUG-D1：手机布局无法进入 Known Hosts 页

**位置**：`client/app/lib/ui/shell.dart:252-258`

```dart
const _compactNav = [(dns, 'Hosts'), (key, 'Keys'), (code, 'Snippets'), (history, 'Logs')];
const _compactNavTarget = [0, 1, 3, 5];
```

底栏只映射 navIndex 0/1/3/5，其中 **Snippets 是 M2 占位页**（Logs 已在 523a4bd 实页化），而已上线的 F4.4 Known Hosts（navIndex 4）没有手机入口——注释"只收纳有实质功能的页"与实际收纳内容不符。`KnownHostsPage` 在 compact 布局下完全不可达。

**期望语义依据**：PRD F4.4 为 P0（`docs/eterm-产品设计与需求文档-v2.md:205`），且 F3.2 Android 客户端功能面"同上"（`:198`）；F4.4 验收场景含手机直连（`:206`）。

**实测输出**（500×800 compact 布局，在最新 HEAD 523a4bd 上复现）：

```
BUG-D1 证据: 手机底栏入口 = [Hosts, Keys, Snippets, Logs]（Snippets 为 M2 占位页，无 Known Hosts）
Expected: exactly one matching candidate（text "Known Hosts"）
Actual: Found 0 widgets with text "Known Hosts": []
```

**修复建议**：`_compactNav` 收入 Known Hosts（`_compactNavTarget` 加 4）；若嫌 5 项拥挤可替换掉一个占位页。

### BUG-D2：关闭当前查看标签左侧的标签后跳到错误会话

**位置**：`client/app/lib/ui/shell.dart:71-80`（`closeTab`）

```dart
void closeTab(int i) {
  setState(() {
    tabs.removeAt(i);
    if (tabs.isEmpty) { activeTab = -1; }
    else if (activeTab >= tabs.length) { activeTab = tabs.length - 1; }
  });
}
```

只处理了"删尾越界"回退，**没有 `if (i < activeTab) activeTab--`**。当被关标签位于当前激活标签左侧时，`activeTab` 数值不变但所指会话右移一位 → IndexedStack 显示右侧邻签的会话。

**复现步骤**：开 3 个终端（alpha/beta/gamma，activeTab=2）→ 切到 beta（activeTab=1）→ 关闭 alpha（i=0 < activeTab=1）→ 界面从 beta 会话跳到 gamma 会话。

**实测输出**（900×700 桌面布局）：

```
BUG-D2 证据: closeTab(0) 后 activeTab = 1（期望 0，即仍查看 beta）
Expected: <0>
Actual: <1>
```

**修复建议**：`tabs.removeAt(i)` 后补 `else if (i < activeTab) activeTab--;`。

## 6. 附加观察（未列入 bug：影响待评估或无法在本机实证）

1. **HostsPage.initState 在 build 栈内同步触发壳层 setState**：`hosts_page.dart:39` 的 `widget.app.refresh()` 是 async 函数，但首段（`loading=true; notifyListeners()`）同步执行于 `initState`（即 IndexedStack 挂载/构建阶段），`shell.dart:117` 随即 `setState` → debug 模式触发 `markNeedsBuild during build` 断言。评审的 widget 测试中**确凿观察到首帧 build 中断**（compact 布局下底栏未完成挂载，需强制补一帧 rebuild），真机表现待复验；建议把首帧通知挪到 `scheduleMicrotask`/首帧之后，或壳层改用 `ListenableBuilder`。
2. **Android 登录上报 platform='macos'**：`api_client.dart:64` 的 `platform` 默认 `'macos'`，`login_page.dart:49-53` 调用时未传 → Android 设备在服务端登记为 `eterm-mobile`/`macos`。两个 Android 设备同 (user, name, platform) 会复用同一 device 行并互踢 token（`userstore.ts:98-124` 的复用语义）。本机无法模拟 Android，故未列入；建议登录页按平台传值。
3. **离线启动丢用户名展示**：`main.dart:129` 期待会话第 3 元素，但 Rust `restore_session` 只返回 `[server, token]`；登录时 `kv_put('username')` 保存了却从未在启动链路读回，离线进入时标题显示 `eterm · `（空）。
