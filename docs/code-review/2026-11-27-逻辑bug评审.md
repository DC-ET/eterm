## 1. BUG-1（P2，server）：WS 变更通知不按 vault 过滤 —— 跨租户全局广播（成文设计的加固缺口）

**位置**（三处叠加构成缺陷，任何单处都看不出问题）：

- `server/src/hub.ts:3-24`：`Hub` 的订阅/广播原语只有 `(rev: number) => void`，**没有 vault 维度**；
- `server/src/syncengine.ts:68`：`if (anyOk) this.hub.broadcast(maxRev)` —— push 成功后把**全局 rev**广播出去，不带 vaultId；
- `server/src/api/app.ts:422-428`：`wsHandler` 里 `deps.hub.subscribe((rev) => { socket.send(...) })` —— **每个已认证客户端订阅全部广播**，无任何过滤。

**影响**（已实测证实）：

1. **跨租户信息泄露**：vault B 每次 push，vault A 的在线客户端都会收到 `{"type":"change","rev":N}`。rev 是 changes 表全局自增 id——长期观测可推断**其他租户的变更频率、活跃时段、数据量级**。vault 是本项目的租户边界（`docs/plan/eterm-技术方案.md:536` 威胁模型："vault 维度鉴权（token ↔ user ↔ vault 归属校验）"），数据面隔离做得很好，通知面却全通。
2. **全员无效唤醒**：每次任何 vault 的 push 都会把**所有**在线设备 poke 起来做一次 pull（对账模型：WS 只当信号，收到就拉）——`realtime.dart:100-105` 有 800ms 去抖合并密集广播，并非逐帧唤醒，但每个去抖窗口后的那次 pull 仍是无谓的（拉不到任何本 vault 变更）；移动端点亮无线、耗电耗流量，多租户共用中枢时放大。
3. ~~与 BUG-2 有耦合~~（**复核撤回**）：初稿称「全员立刻拉把 pull 精确送进竞态窗口」——800ms 去抖窗口远大于 pushItem 事务时长，该耦合论述不成立；BUG-2 的触发不依赖本条（见 §2 修订）。

**期望语义依据（复核修订）**：技术方案 §「WS 通知」（`docs/plan/eterm-技术方案.md:274`）明文「服务端不做数据推送、**不做订阅过滤**」——全局广播是**成文设计**，本条属「多租户加固缺口」而非实现违约（初稿仅引威胁模型行，系选择性论证，已修正）。但同一方案的威胁模型（:536）把 vault 维度鉴权列为公网 API 防线：自建单租户时「不做过滤」无伤，**公网多租户中枢**（项目明确设想的部署形态）下两者相互矛盾——数据面隔离得再好，通知面全通仍削弱租户边界。修复定性为加固而非修 bug。

**复现与实测输出**（`review2-verify.spec.ts` BUG-A 用例：carol/bob 两用户两 vault，carol 挂 WS，bob 在**自己的 vault** push 一台主机；断言 carol 的 WS 不得收到任何帧、carol 的 pull 无新变更）：

```
BUG-A carol(他 vault) WS 实际收帧: ["{\"type\":\"change\",\"rev\":1}"]
INFO http GET /api/v1/sync/pull?cursor=0 ...        ← carol 被 poke 后拉了个寂寞
AssertionError: expected [ '{"type":"change","rev":1}' ] to have a length of +0 but got 1
```

carol 的 pull 返回 0 条变更（bob 的数据不属于她）——收到的帧纯属他 vault 噪声。

**修复建议**：订阅带上 vault 维度——`Hub.subscribe(vaultId, fn)` / `broadcast(vaultId, rev)`；`wsHandler` 用 `ctx.vaultId` 订阅，`SyncEngine.push` 把 `vaultId` 传给 broadcast。改动集中在 3 处、共约 10 行，wire 帧形状不变（客户端只判 `"change"` 子串，兼容）。落地时同步更新技术方案 §「WS 通知」的「不做订阅过滤」表述，避免设计与实现再次脱节。

## 2. BUG-2（P1，server）：pull 游标可越过未提交事务的 id 空洞 —— 已提交变更对客户端永久不可见

**位置**：

- `server/src/store/syncstore.ts:47-49`：pull 主查询 `SELECT id ... FROM changes WHERE id > ? AND vault_id = ? ORDER BY id ASC` —— 游标按 changes 表**全局自增 id** 推进；
- `server/src/store/syncstore.ts:98`：`newCursor = trimmed[trimmed.length-1].id` —— 客户端把游标落到**本次看到的最大 id**；
- `server/src/store/syncstore.ts:317-333`（`allocRev`）：changes 行在 pushItem **事务内** INSERT（取得自增 id）、随事务一起 COMMIT。

**机理**：InnoDB 的自增 id 在 INSERT 时即分配，**分配顺序 ≠ 提交顺序**。同 vault 两个并发 push 事务 T1、T2（不同设备同时编辑不同实体）：

```
T1: BEGIN → ... INSERT changes(id=100) → UPDATE entity → (未提交)
T2: BEGIN → INSERT changes(id=101) → COMMIT ─┐   ← T2 后分配 id 却先提交
客户端 pull（此刻）：可见 [.., 101]，未见 100     │   ← 游标落到 101 并持久化
T1: COMMIT ────────────────────────────────────┘   ← id=100 的变更从此 id < 101
客户端下次 pull：WHERE id > 101 → id=100 永远不可见
```

**影响**（复核精确化）：被跳过的那条 **change 行**对本设备永久不可见——客户端游标只增不减（`store/mod.rs:169-187` 的 cursor kv），lib/ 无任何全量对账/定时器/冲突折叠（`api_client.dart:117` 的 `pullAll` cursor=0 全量重放已无调用方，是死代码），唯一恢复手段是登出重登（`clear_local` 清游标后从 0 全量拉）。对**实体状态**的影响分两类：

- 该实体**随后再有任何变更**：pull 每次返回实体当前整行（`syncstore.ts:73-96`），后续变更会把终态（含被跳过的编辑）一并带回——属延迟收敛，非永久；
- 该实体**此后不再变更**（典型受害形态）：漏掉的 tombstone → 本地幽灵实体一直显示在列表里；漏掉的 upsert → 本地 base_rev 陈旧 → 该实体在本设备**每次编辑都 conflict**（客户端不折叠 server_data，各 push 方法只抛「推送被拒」）→ 死循环直到登出清库。

后一类是真正的永久性静默分叉，直击多端同步这一核心卖点。触发概率自评为低（pushItem 事务亚毫秒级窗口 × 同 vault 并发 push × 拉取恰落在窗口内），但系统长期 24×7 运行会累积发生，且发生后**无任何报错**：

1. ~~BUG-1 的全局广播把 pull 送进窗口~~（**复核撤回**：`realtime.dart:100-105` 的 800ms 去抖远大于事务时长，且 BUG-2 不依赖 BUG-1 触发）；
2. 系统长期运行（多设备、频繁编辑），小概率事件必然累积发生。

**复现与实测输出**（BUG-B 用例：先用真实 `pushItem` 落 H 与 J 两台主机，中间用独立连接复刻一个「进行到 allocRev 之后、COMMIT 之前」的悬挂事务（INSERT changes + UPDATE 实体，与 pushItem 事务内的写集相同）；悬挂期间 pull 一次，提交后再 pull 一次）：

```
BUG-B 提交前 pull: [{"rev":2,"id":"01a21c1e"},{"rev":4,"id":"01a21c1e"}] cursor = 4
    ↑ 悬挂事务的 change id=3 不可见（InnoDB 快照，正常）；但游标已推进到 4
BUG-B 提交后 pull(cursor=4): []
    ↑ 悬挂事务此刻已提交（这是一次完全合法成功的 push）——H 的更新对游标 ≥4 的设备永久不可见
AssertionError: expected 0 to be greater than 0
```

（`id` 前缀相同是 uuidv7 时间戳前缀巧合；rev=2 是 H 初建、rev=3 是 H 的悬挂更新、rev=4 是 J。）

**修复建议**（择一，推荐 ①）：

1. **同 vault push 串行化**：pushItem 事务开头对 vault 行加锁 `SELECT rev FROM vaults WHERE id = ? FOR UPDATE`——任何同 vault 事务不可能出现「后 id 先提交」，空洞不可能形成；跨 vault 仍并发（性能不受影响）。
2. changes 行移到**提交后**写入（两阶段：先提交实体事务，再独立短事务插 changes）——id 分配顺序即提交顺序；代价是实体与 change 的原子性拆开（需处理中间态）。
3. 客户端兜底：定期（如每日/每次启动）以 cursor=0 做一次全量折叠对账，把「静默分叉」降级为「延迟收敛」——无论服务端选哪种修法，这层保险都值得加。

## 3. BUG-3（P1，client）：删除运行中的端口转发规则不停止转发（僵尸隧道）

**位置**：`client/app/lib/ui/port_forwarding_page.dart`

```dart
// :96-99  _stop 开头
Future<void> _stop(PortRuleView r) async {
  if (_busy.contains(r.id)) return;
  final fwd = _forwards.remove(r.id);   // ← remove 的返回值被当“是否在运行”判据
  if (fwd == null) return;              // ← 拿不到就早退：pf_close_forward/pf_disconnect 都不执行
  ...
// :174-175  _confirmDelete 确认删除后
  final running = _forwards.remove(r.id);      // ← 先把 map 条目摘掉！
  if (running != null) await _stop(r);         // ← 再调 _stop：它 remove 到的是 null → 原路 return
```

`_confirmDelete` 的 `_forwards.remove(r.id)` 是复制粘贴残留（`_stop` 自己会 remove），两者的组合让 `_stop` 在删除路径上**永远走 `fwd == null` 早退**。

**影响**：

1. **删除的规则隧道还在跑**：Rust 侧 `pf_listen` 起的 TcpListener 与 accept 循环无人叫停（`pf_close_forward` 未调用）——本地端口继续被占用、**经 SSH 隧道继续转发流量**。用户删规则的意图（多半是不再想要这条通路/端口）被静默违背，且 UI 已无任何“运行中”指示（`_forwards` 已摘除）→ **不可见的僵尸隧道**。
2. **SSH 会话泄漏**：`pf_disconnect` 同样不执行（`:108-116` 的 stillUsed 判断在早退之后）；泄漏的会话要等到用户切走 Port Forwarding 页触发 `dispose()`（`:30-37` 全量断开）才回收——停留在页面上就一直活着。
3. 对比同文件 `_stop` 直调路径（用户点「停止」按钮）完全正常——**同一功能两条路径，一条停、一条不停**，行为不对称本身即缺陷证据。

**复现与实测输出**（受 FFI 限制的验证方式说明：`_start` 需要真实 `pf_connect` 才能把 `_forwards` 填成运行态，flutter test 无法驱动真实 State 的私有字段。取证用例**逐字复刻** `_stop`（:96-121）与 `_confirmDelete` 停转发段（:174-175）的控制流，仅把 pf FFI 换成调用记录器——代码对照见 §8）：

```
BUG-C 删除运行规则后的 pf 调用记录: []                    ← pf_close_forward / pf_disconnect 均未调用
BUG-C _forwards 残留: {} / _sessions 残留: {h1: 111}     ← map 已清空（UI 显示已删）但 SSH 会话还在
AssertionError: Expected: non-empty / Actual: WhereIterable<String>:[]

BUG-C 对照组（_stop 直调）pf 调用记录:
  [pf_close_forward(session=111, fwd=222), pf_disconnect(session=111)]   ← 不先 remove 时一切正常
```

**修复建议**：`_confirmDelete` 删除预摘除，改为 `if (_forwards.containsKey(r.id)) await _stop(r);`（`_stop` 内部语义不变）；或 `_stop` 改为接受转发 id 入参、不再用 map remove 的返回值做控制流判据。修法一行级，但建议顺带补一条「删除运行中规则必须停隧道」的回归用例（把 pf 调用做成可注入记录器即可，无需真机）。

## 4. BUG-4（P2，client）：登录链路 WS poke 非静默 —— 违反对账静默契约

**位置**：

- `client/app/lib/ui/login_page.dart:71`：`realtime.start(server, result.token, poke: app.refresh);` —— 传的是**无参 tear-off**，等价 `refresh(silent: false)`；
- 对照 `client/app/lib/main.dart:128-129`（启动链路）：`realtime.start(sess[0], sess[1], poke: () => app.refresh(silent: true));`
- 契约自述 `client/app/lib/services/app_state.dart:763-766`：`refresh([silent])` 文档明确「切页回来、**WS 推送对账**等后台场景——用户已经在看内容，别再闪一下」，`silent=false` 还会同步置位顶部 2px 加载条。

## 5. BUG-5（P2，client，上轮遗留）：登录上报 platform 恒为 'macos'

**位置**：

**复现与实测输出**（BUG-E 用例：本地假中枢捕获登录请求体，按 login_page 在 Android 上的实际调用形态 `api.login('bob', 'pw', deviceName: 'eterm-android')`）：

## 7. 附加观察（未列为 bug：影响待评估或属设计取舍）

1. **离线启动丢用户名**（上轮观察 3，仍未修）：`main.dart:131` 期待会话第 3 元素，但 `rust/src/api/local.rs:25-30` 的 `restore_session` 只返回 `[server, token]`；登录时 `kv_put('username')` 落了盘却从未在启动链路读回——离线进入时 Settings 页账号区显示「?」+ 空用户名。修复只需 boot 时 `kv_get('username')` 兜底。
2. **LoginPage._submit 只捕获 `ApiException`**（`login_page.dart:81`）：登录 API 成功后 `local.saveSession`/`kvPut`（FFI）若抛错（磁盘满/本地库损坏），异常逃逸出 try——release 下被 zone 吞掉，用户停在登录页无任何提示、不知已登录成功。建议 catch 面放宽并给出「本地存储失败」文案。
3. **进程内 Map 无淘汰**（`api/app.ts:89` `buckets`、`:107` `lastSeen`）：按 IP 键无界增长。自建 + IP 白名单部署下影响有限；若有人直暴公网需补 LRU/TTL。
4. **改密不吊销其他设备 token**：`api_client.dart:90` 注释自述「成功后其余会话仍有效」为设计；与「设备失窃→改密自救」的直觉有距离，建议至少在设置页改密成功文案中明示「如需踢出其他设备请到设备管理页吊销」。（复核确认：威胁模型对「设备失窃」的缓解即设备吊销而非改密，属成文设计取舍，仅文案建议。）
5. **`tar_download_inner` 相对路径语义**（`sftp.rs:855-860`）：`dir="foo"`（相对）会被拆成 `tar -C / foo`（错目录）；当前调用链恒为 realpath 后的绝对路径（`_joinRemote` 从 `/` 起），仅作防御性记录——加一行 `if !dir.starts_with('/') return Err` 即可封死。
6. **同平台固定设备名互踢（复核勘误带出，已实测）**：`login_page.dart:57-63` 设备名按平台固定（'eterm-mac' 等），`userstore.ts:121-148` 按 (user, name, platform) 复用 device 行并覆写 token_hash → 同平台第二台设备登录后，第一台的 token 立即 401 被踢回登录页——**用户无法在两台 Mac（或两台 Android）上同时保持登录**。上轮观察 2 的原始场景，初稿误以为「分端后已消除」，复核实测确认其残余部分仍在：`同平台互踢: 旧 token /me = 401 / 新 token /me = 200`；对照组（不同 device_name）双 token 并存通过。修复见 BUG-5 修复建议（设备名唯一后缀）。取证用例见 §8.4。

// BUG-C 说明：_PortForwardingPageState 的字段/方法私有且 _start 需要真实 pf_connect

class _PfRecorder {
  final List<String> calls = <String>[];
  void closeForward(BigInt sessionId, BigInt fwdId) =>
      calls.add('pf_close_forward(session=$sessionId, fwd=$fwdId)');
  void disconnect(BigInt sessionId) => calls.add('pf_disconnect(session=$sessionId)');
}

class _Rule {
  _Rule(this.id, this.hostId);
  final String id;
  final String hostId;
}

/// 逐字复刻 port_forwarding_page.dart:96-121 的 _stop。
/// hosts 对应 widget.app.hosts（_hostOf 的查找域）。
Future<void> _stopReplica(
  _Rule r,
  _PfRecorder rec,
  Map<String, BigInt> sessions,
  Map<String, BigInt> forwards,
  Set<String> busy,
  List<_Rule> allRules,
  Set<String> hosts,
) async {
  if (busy.contains(r.id)) return;
  final fwd = forwards.remove(r.id);
  if (fwd == null) return;
  busy.add(r.id);
  try {
    final host = hosts.contains(r.hostId) ? r.hostId : null; // 对应 _hostOf(r)
    final session = host == null ? null : sessions[host];
    if (host != null && session != null) {
      final hostId = host;
      rec.closeForward(session, fwd);
      final stillUsed = forwards.keys.any((rid) {
        _Rule? other;
        for (final x in allRules) {
          if (x.id == rid) {
            other = x;
            break;
          }
        }
        return other != null && other.hostId == hostId;
      });
      if (!stillUsed) {
        rec.disconnect(session);
        sessions.remove(hostId);
      }
    }
  } finally {
    busy.remove(r.id);
  }
}

  _Rule r,
  _PfRecorder rec,
  Map<String, BigInt> sessions,
  Map<String, BigInt> forwards,
  Set<String> busy,
  List<_Rule> allRules,
  Set<String> hosts,
) async {
  // ...用户已在对话框确认（ok == true）...
  final running = forwards.remove(r.id); // ← port_forwarding_page.dart:174
  if (running != null) await _stopReplica(r, rec, sessions, forwards, busy, allRules, hosts); // ← :175
}

    // 且该会话上没有其他规则时应断开 SSH（pfDisconnect）。

  test('BUG-C 对照组：直接点「停止」按钮（不先 remove）路径工作正常', () async {
