## 1. BUG-1（P0，正确性/数据丢失）：deleteHost 墓碑共享密钥——多主机共用 Keychain 密钥时删一台主机毁掉其余主机的凭据

**位置**：`client/app/lib/services/app_state.dart:608-643`（`deleteHost`，既有代码未改），与本次新增的共享入口交互：
- `app_state.dart:571-589`（`addHost` 的 `existingKeyId` 直指既有 `identity.key_id`，不新建实体）；
- `app_state.dart:719-721`（`editHost` 的 `replaceWithKeyId` 换绑任意 Keychain 密钥）。

```dart
if (h.identityId != null) {
  ...
  tomb('identity', identityId);
  if (keyId != null) tomb('ssh_key', keyId);   // ← 无条件墓碑密钥
}
```

**问题**：本次变更加入了"多台主机共享一把密钥"的数据形态（Keychain 复用正是 M1 收口的核心卖点），但 `deleteHost` 仍沿用旧假设"host ↔ identity ↔ ssh_key 三者 1:1"，删除主机时**无条件把 identity 引用的 ssh_key 一并墓碑**，不检查该密钥是否被其他 identity/主机引用。对比同文件 `deleteKey`（`:267-271`）明确做了 `usedBy.isNotEmpty` 守卫并提示"请先在这些主机的编辑里更换凭据"——两条删除路径的守卫不对称。

**影响**（确定性，普通 UI 流程即可触发）：
1. 主机 A、B 都通过"从 Keychain 选择"引用密钥 K；删除主机 A → K 被墓碑 → 增量同步后 B 的 `credentialFor`（`:198-215`）查不到 `ssh_key/K` → 返回 null → B 变"无凭据"不可连接；
2. Keychain 页中 K 消失。对**生成型密钥**（`generateKey` 只入 vault，从不落盘）这是 vault 内唯一副本的丢失；对导入型密钥用户也未必还留有源文件。恢复只能靠重新导入/生成并重新部署公钥到所有目标机。

**期望语义依据**：PRD 的密钥引用模型（identity.key_id 引用）+ 本次功能注释本身（`app_state.dart:267`："引用中的密钥删除会造成 identity 悬空"——deleteHost 恰恰制造了这种悬空的反向破坏）。`deleteKey` 已有的守卫文案即本项目对该风险的正式态度。

**复现要点**（本次评审静态推演 + wire 语义核对，未在生产 vault 实删）：push 的 `op=delete` 带 `base_rev` 乐观锁会被服务端接受（`syncstore.ts:204-213`，删除不做引用检查）→ pull 下发墓碑 → 本地库折叠移除实体。

**修复建议**：`deleteHost` 中 `tomb('ssh_key', keyId)` 前先统计该 keyId 被多少个 identity 引用（`_entities` 中 `identity/*` 的 `key_id`），引用数 > 1 或该密钥在 Keychain 中仍存在且被其他主机使用时**不墓碑密钥**；只有确认 1:1（旧数据形态）才保留现行为。可复用 `keys` 视图的 `hostsOfKey` 统计逻辑（`:218-245`）。

## 2. BUG-2（P1，正确性）：空 `public_key` 的密钥"部署公钥"静默假成功

**位置**：`client/app/lib/services/app_state.dart:391-411`（`deployPublicKey` 无内容守卫）、`:413-421`（`deployCommandFor` 对空串不设防）、`:574-584`（旧 addHost 路径建的 ssh_key 实体 `public_key: ''`、`fingerprint: ''`）；UI 入口 `lib/ui/keychain_page.dart:846-857`（部署按钮对空公钥照常可用）与 `:901-902`（详情页公钥显示"—"，但按钮不禁用）。

**问题**：Keychain 里的存量密钥有一类 `public_key` 为空——所有经旧版 `addHost`（粘贴 PEM）创建的 ssh_key 实体都写了 `public_key: ''`（`:579`、`:727`），它们现在同样出现在 Keychain 列表并可点"部署公钥"。此时 `deployCommandFor('')` 生成的命令是：

```sh
... && grep -qxF '' ~/.ssh/authorized_keys 2>/dev/null || printf '%s\n' '' >> ...
```

`grep -F ''` 空 pattern 的语义坑：
- **GNU grep（Linux 目标机）**：空串匹配任何行 → 文件非空即 exit 0 → `||` 短路 → **什么都不追加**，命令整体 exit 0；
- **BSD grep（macOS 目标机）**：空 pattern 不匹配（本机实测 exit 1）→ 追加**一行空行**，命令同样 exit 0。

两种情况客户端都看到 `exit_code == 0`（`app_state.dart:404`）→ 弹"公钥已部署到 xxx"并记 `key_deploy` 成功事件——**实际既没部署也没报错**。

**本机取证**（`/tmp` 沙盒 HOME、`/bin/sh`）：

```
run1 exit=0 authorized_keys: ssh-ed25519 AAAA test      ← 正常路径部署成功
run2(idempotent) exit=0 wc -l = 1                        ← 幂等去重正确
grep -qxF ''（文件已有 1 行） → 退出 0（GNU 语义）/ 本机 BSD 退出 1 后追加空行
两种 grep 行为下结果一致：exit 0 + 公钥未部署 → 客户端报成功
```

**影响**：用户对旧格式密钥执行部署 → 假成功 → 到目标机用该密钥认证失败（authorized_keys 根本没有公钥）。失败被成功提示掩盖，排障成本高。新导入/生成的密钥经 Rust `inspect` 必有 `public_key`，故仅存量数据踩坑——但存量数据正是本功能要收口的对象。

**修复建议**（两层都加）：
1. `deployPublicKey` 开头守卫：`k.publicKey.trim().isEmpty` → 抛"该密钥没有公钥行（旧版导入），请重新导入或改用新密钥"；
2. `deployCommandFor` 对清洗后为空的行抛 `ArgumentError`（防其他调用方绕过）；
3. 可选：`_DeployHostPickerDialog`/详情页对 `publicKey.isEmpty` 的密钥禁用部署按钮并提示。

## 3. 重点安全面核查（确认无问题）

以下为任务书点名的 P0 安全项，逐项核实**均未发现问题**（列出证据）：

1. **deployCommandFor 注入面**（`app_state.dart:413-421`）：公钥行在拼入单引号 shell 串前剔除 `'`/`\r`/`\n`。单引号语境下 POSIX shell（及 fish/csh 非交互）除 `'` 外一切字面，`'` 已被移除 → 不可逃逸引号、不可拆分第二条命令。测试 `test/keychain_test.dart:253-256` 验证引号总数恒为 6、无换行残留。本机 `/bin/sh` 沙盒实测：幂等追加 + `grep -qxF` 去重行为正确。剩余缝隙见 OBS-7（撇号被删而非转义）。
2. **ssh_exec_oneshot 凭据/命令处理**（`rust/src/api/keychain.rs:44-90`）：async（非 sync）✓；整体 20s `tokio::time::timeout`（含建连/认证/exec/收尾）✓；TOFU 复用 `crate::api::ssh::connect_and_auth` → `store::tofu_decide`（与终端/SFTP 同一套 known_hosts，首连自动记录、指纹不符拒绝并给出可读原因，`ssh.rs:63-77、88-135`）✓；TOFU 拒绝/认证失败/超时三条错误路径均返回可读字符串，**不含 secret**；`exec_on` 对 EOF/Close/ExitStatus 的处理正确，短生命周期通道不会悬挂（超时兜底）。frb 执行器走 `ssh_runtime().spawn` + oneshot 通道，与 portfw.rs 同模式（frb 无 tokio reactor 陷阱）✓。
3. **私钥内容不落日志/事件**：`app_state.dart` 的 `logEvent` detail 只含 label/类型/主机名（`:305、322、373、409、287`）；`keychain.rs` 全文无 print/tracing；错误串只有推送状态、远端 stderr（公钥非私密，且不含私钥）、Rust 解析错误消息。`api.push` 请求体经 TLS 到中枢并静态加密（架构约定）， pull 明文仅驻内存/本地加密库。
4. **wire 契约（P0 正确性重点）**：
   - `renameKey`（`app_state.dart:354-376`）：`_update` 取 `_entities` 快照 `rev` 作 `base_rev`（pull 行含 `rev`——`server/src/store/db.ts:157` `rowToWire` 回填，核实无误）；显式回传全部 7 个 wire 字段；`private_enc` 原样回传 → 服务端 `checkKeyImmutability`（`syncstore.ts:236-266`）解密比对通过 ✓（本地快照明文与服务端 `openField` 解密明文同源）。
   - `editHost`（`app_state.dart:702-750`）：`group_id` 无条件显式发（含 null=移出分组，规避 `?null` 省键陷阱）✓；identity 发 `password_enc: null` 显式清列 ✓；换绑/替换二选一互斥正确。
   - `addHost` vault 复用（`:571-589`）：不推 ssh_key 实体（回归测试断言）✓；identity 为**新实体 INSERT**，缺 `password_enc` 键 → `insertEntity`（`syncstore.ts:278-285`）落 NULL，语义正确（但见 OBS-1）。
   - push 结果校验：所有新方法都检查 `results` 非 ok 项并抛错（`_pushKeyEntity:346-349` 等）✓；被拒后不写事件、不 refresh，本地状态不脏。
5. **api_client charset 修复**（`api_client.dart:35-40`）：`_headers()` 为全部请求共用；dart:io `HttpClientRequest.write` 依 content-type charset 选编码，显式 `charset=utf-8` 后中文请求体（标签/口令/密钥注释）不再 latin1 抛错。修复正确且覆盖面完整。
6. **frb sync/async 语义**：`sshExecOneshot` async ✓（网络）；`keyGenerateEd25519`/`keyInspect` sync —— 均纯 CPU：Ed25519 生成走 `russh-keys` `SigningKey::generate(&mut OsRng)`（毫秒级，RNG 安全），`decode_secret_key` 对 Ed25519/PKCS#8 解析为毫秒级；不违反"可能阻塞（网络/IO）必须 async"的约束（边界见 OBS-8）。
7. **openssh-key-v1 手工编码**（`rust/src/util/sshkey.rs:37-85`）：known-answer 测试（seed=[42;32]）的指纹/公钥行与本机 `ssh-keygen` 交叉验证一致；编码结果经 `decode_secret_key` 回读（解码器内部校验 seed→pub 推导）；padding 语义（已对齐可为空）与 OpenSSH 一致。检查 int 用 `rand::random()`（thread_rng，非密钥材料）无碍。
8. **事件 kind 一致性**：Dart 侧新 kind `key_import/key_generate/key_edit/key_deploy/key_delete` 与 `store/mod.rs:340` 注释一一对应 ✓。
9. **依赖**：`ed25519-dalek` 仅 dev-dependencies（主代码只用 russh-keys 内部类型）；`file_selector` 已是既有依赖（SFTP 用），无 pubspec 变更。

## 4. 建议与观察（未列为 bug）

- **OBS-1（测试有效性）** `test/keychain_test.dart:180-181`：`expect(data['password_enc'], isNull)` 对"键缺失"与"显式 null"都通过，而用例理由声称验证"显式 null 才清列"。当前 addHost vault 分支（`app_state.dart:585-589`）确实没发 `password_enc` —— 对 INSERT 无害，但建议补 `'password_enc': null` 并把断言改为 `containsPair('password_enc', null)`，让契约意图可被回归锁定。
- **OBS-2（悬空引用）** `app_state.dart:571、719`：`existingKeyId`/`replaceWithKeyId` 来自打开对话框时的快照，他端并发删除该密钥后 push 仍成功（服务端 identity.key_id 无 FK/存在性校验）→ 悬空 key_id，主机"无凭据"。建议提交前校验 `_entities.containsKey('ssh_key/$id')`。
- **OBS-3（守卫盲区）** `app_state.dart:267-271`：`usedBy` 只统计"protocol→identity→key"链；identity 无 host_protocol（多实体 push 部分成功可产生）时引用不计入，deleteKey 可删出悬空 identity。建议 usedBy 统计直接数 identity 的 key_id 反向引用。
- **OBS-4（去重）** `app_state.dart:294-308`：同一 PEM 重复导入产生多个实体（服务端对 fingerprint 无唯一约束）。建议 importKey 前按 fingerprint 查重提示，或后端按 (vault_id, fingerprint) 唯一。
- **OBS-5（输入清洗）** `rust/src/util/sshkey.rs:90-99`：comment 未滤 `\r\n`/控制字符（`_GenerateKeyDialog` 的备注框也无 inputFormatters），多行备注使 `public_key_line` 变多行入库；deploy 侧清洗兜底了注入风险，但展示与 authorized_keys 粘贴会异常。建议 Rust 侧 trim + 滤控制字符。
- **OBS-6（UX 状态残留）** `add_host_dialog.dart:106-117`：`_secret` 在认证来源/方式切换间不清理，先粘 PEM 再切"从 Keychain 选择"再切回"口令"，PEM 文本以密文形式残留在口令框中会被当口令保存。建议切到 vault 来源时清 `_secret`。
- **OBS-7（清洗副作用）** `app_state.dart:416`：含撇号的公钥 comment 被删字符后与 Keychain 详情页复制的公钥行不一致（幂等判断依然自洽，仅展示/比对外观问题）。建议改用 `'\''` 转义保留原字符。
- **OBS-8（sync 边界）** `rust/src/api/keychain.rs:20-23`：`keyInspect` 对输入无长度上限，超大粘贴文本在 UI 线程解析。建议入口处限制（如 64KB）并提前拒绝。
